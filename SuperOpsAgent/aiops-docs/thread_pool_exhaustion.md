# 应用线程池耗尽告警处理方案

## 告警名称与影响

- **告警名**: `ThreadPoolExhausted`
- **触发条件**: 活跃线程接近最大线程数且队列长度持续增长，或日志出现 `RejectedExecutionException`、任务提交被拒绝。

线程池耗尽会使新任务无法执行，表现为接口排队、超时和错误率升高。仅增大线程数可能进一步放大下游数据库或外部服务压力。

## 排查步骤

1. 查看核心线程数、最大线程数、活跃线程、队列长度、拒绝次数和任务执行耗时。
2. 识别占用线程最长的任务类型，关联数据库、Redis、外部 API 和文件操作的延迟。
3. 检查是否有同步阻塞、锁竞争、无限等待或异常重试导致线程无法释放。
4. 对比流量和线程池指标，判断是业务峰值还是单个慢任务拖垮全部线程。

## 常见原因与处理

### 原因1：下游调用阻塞

**特征**：线程大部分处于等待外部 API、数据库或网络响应状态，任务耗时明显升高。

**处理方案**：设置连接和读取超时；启用熔断或降级；将非关键同步调用改为异步处理。

### 原因2：队列堆积或拒绝策略不合理

**特征**：队列持续增长，达到上限后任务被拒绝，调用方没有处理拒绝异常。

**处理方案**：为队列长度和拒绝次数建立告警；对可延迟任务限速或转入消息队列；明确拒绝后的降级行为。

### 原因3：线程数配置不匹配

**特征**：正常流量下也接近上限，CPU 利用率不高但队列增长，或线程过多导致上下文切换明显。

**处理方案**：依据任务是 CPU 密集还是 I/O 密集重新设置线程数；配合下游容量设置并发上限；通过压测验证。

## 验证与预防

验证活跃线程、队列长度和拒绝次数恢复基线，接口 P99 和错误率下降，下游资源未被新增并发压垮。持续监控任务耗时、队列、拒绝和线程状态；为不同任务类型使用隔离线程池。
