# 消息消费者延迟告警处理方案

## 告警名称与影响

- **告警名**: `ConsumerLagHigh`
- **触发条件**: 消费组延迟连续 10 分钟超过业务时效，或消费位点推进速度持续低于消息生产速度。

消费者延迟会使消息虽已进入队列但不能按时完成处理，影响订单同步、通知、风控或数据更新；延迟恢复时的集中处理还可能冲击下游。

## 排查步骤

1. 按消费组和分区查看 Lag、生产速率、消费速率及在线消费者数。
2. 检查消费者日志中的反序列化失败、业务异常、提交位点失败和重平衡事件。
3. 抽样分析单条消息处理耗时，关联数据库、Redis、外部 API 的延迟和错误。
4. 确认是否发生扩容、发布、分区变化或批量回放，避免把重平衡误判为业务处理变慢。

## 常见原因与处理

### 原因1：消费者频繁重启或重平衡

**特征**：在线实例数波动，日志反复出现加入和离开消费组，位点推进间断。

**处理方案**：先修复实例崩溃、健康检查或网络问题；减少不必要的消费者滚动重启；等待分区分配稳定后再观察 Lag。

### 原因2：单条消息处理过慢

**特征**：消费者在线但吞吐下降，处理耗时集中在数据库或外部调用。

**处理方案**：优化慢 SQL 或外部调用超时；将可批量的操作批量化；降低单条消息中的同步工作量。

### 原因3：提交位点失败

**特征**：业务处理日志存在但重启后重复消费，日志出现提交失败或协调器异常。

**处理方案**：确认消息处理与位点提交顺序；修复认证或网络问题；对幂等处理使用业务去重键。

## 验证与预防

验证消费位点持续推进、消费速率高于生产速率、Lag 连续下降，且消费者无频繁重平衡。监控 Lag、位点提交失败、处理耗时和重平衡次数；在发布和扩容时控制消费组成员变化。
