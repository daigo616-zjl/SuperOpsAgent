# Kubernetes CrashLoopBackOff 告警处理方案

## 告警名称与影响

- **告警名**: `PodCrashLoopBackOff`
- **触发条件**: Pod 在 10 分钟内反复重启，状态为 `CrashLoopBackOff`，或可用副本数低于目标副本数。

反复崩溃会造成实例不可用、流量集中到剩余副本，并可能触发服务不可用或错误率升高。

## 排查步骤

1. 查看 Pod 的事件、当前状态、重启次数和退出码，区分应用退出、探针失败、镜像问题和资源终止。
2. 获取本次及上一次容器日志，重点检查启动配置、依赖连接、端口监听和异常堆栈。
3. 检查 Deployment 的镜像版本、环境变量、ConfigMap、Secret 和最近发布记录。
4. 检查存活探针、就绪探针的路径、端口、初始延迟和超时是否与应用启动时间匹配。

## 常见原因与处理

### 原因1：应用启动异常

**特征**：容器日志有配置解析、依赖连接或端口绑定错误，退出码非零。

**处理方案**：修复配置或依赖可达性；回滚到最近稳定镜像；确认修复后再逐步恢复副本。

### 原因2：探针配置不匹配

**特征**：应用可短暂启动但被探针杀死，事件显示 liveness 或 readiness 失败。

**处理方案**：修正探针路径、端口和阈值；为启动较慢的应用增加合理初始延迟；不要用存活探针检查依赖服务状态。

### 原因3：资源限制过小

**特征**：启动期间 CPU 被限制、内存接近上限或事件出现 OOMKilled。

**处理方案**：区分 CPU 限流和内存不足；按历史峰值调整 requests/limits；修复启动阶段的大对象加载。

## 验证与预防

验证 Pod 重启次数停止增长、就绪副本达到目标、错误率回落，且新版本稳定运行 30 分钟。发布前在预发布环境验证探针和配置；监控退出码、重启次数、探针失败和可用副本。
