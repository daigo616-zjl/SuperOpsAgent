# 数据库死锁告警处理方案

## 告警名称

- **告警名**: `DatabaseDeadlockDetected`
- **告警级别**: 警告；高频发生时升级为严重
- **触发条件**: 数据库死锁错误在 5 分钟内超过设定阈值，或关键业务事务持续回滚。

## 业务影响

死锁会导致其中一个事务被数据库回滚。若应用没有重试机制，用户会看到下单、扣库存、状态更新等请求失败；高频死锁还会造成事务堆积和响应时间升高。

## 排查步骤

### 步骤1：确认错误范围

在应用日志中筛选 deadlock、transaction rollback、lock wait 等关键字，记录业务接口、表名、SQL 模板和发生时间，确认是否集中在某次发布或批处理任务后。

### 步骤2：获取死锁信息

查询数据库死锁日志或引擎状态，识别互相等待的事务、锁定的记录和 SQL 执行顺序。不要只根据单条报错推断根因。

### 步骤3：检查事务边界

确认事务内是否包含外部 RPC、文件操作、循环处理或人工等待；检查同一业务流程是否以不同顺序更新多张表或多条记录。

### 步骤4：检查并发任务

核对定时任务、补数任务和在线请求是否同时更新同一批数据。必要时按业务主键确认是否存在热点记录。

## 常见原因分析

### 原因1：多表更新顺序不一致

**特征**：两类请求更新相同表集合，但一类先更新表 A 再更新表 B，另一类顺序相反。

**处理方案**：统一业务代码中的表和记录锁定顺序；将相关更新收敛到同一服务方法；发布前补充并发事务测试。

### 原因2：事务持续时间过长

**特征**：事务内有慢 SQL、循环批处理或外部调用；锁持有时间明显长于正常请求。

**处理方案**：缩短事务范围；把外部调用移出事务；拆分批处理；为慢 SQL 添加索引或改写查询。

### 原因3：热点记录并发更新

**特征**：死锁集中在同一订单、库存、账户或状态记录；峰值流量时发生频率升高。

**处理方案**：按业务键串行化热点操作；使用队列削峰；减少同一记录的重复更新；对可重试操作增加有限次数重试。

### 原因4：缺少死锁重试

**特征**：数据库仅回滚一个事务，但应用直接将错误返回用户，重试后可成功。

**处理方案**：仅对幂等操作增加带退避的有限重试；记录重试次数；不可幂等的写操作必须先设计幂等键，不能盲目重试。

## 紧急处理措施

1. 确认是否影响核心写入链路和失败比例。
2. 暂停或降速可能与在线请求竞争的批处理任务。
3. 对确认幂等的操作启用有限重试和退避。
4. 针对持续持锁的异常事务按数据库规范处理，并保留死锁日志用于定位。

## 验证步骤

1. 死锁错误数恢复到基线水平。
2. 关键事务成功率恢复正常。
3. 数据库中不存在持续增长的锁等待。
4. 修复后的并发压测不再复现相同的锁顺序冲突。

## 预防措施

- 统一事务中表和记录的访问顺序。
- 控制事务范围和执行时长。
- 对热点写入设计串行化或削峰机制。
- 为死锁、锁等待和长事务建立独立监控。
