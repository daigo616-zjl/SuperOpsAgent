# Kubernetes Pod OOMKilled 告警处理方案

## 告警名称与影响

- **告警名**: `PodOOMKilled`
- **触发条件**: 容器退出原因为 `OOMKilled`，或内存使用持续超过 limit 的 90%。

OOMKilled 会直接终止容器，造成请求中断和实例重启；频繁发生会使服务容量下降，并掩盖真实的内存泄漏或流量问题。

## 排查步骤

1. 查看 Pod 事件、退出码、重启次数和容器 memory limit，确认是否为 OOMKilled 而非普通应用退出。
2. 对比内存曲线与流量、GC、缓存大小、文件导入或定时任务的时间关系。
3. 查看应用日志和堆转储策略，识别内存泄漏、大对象、缓存增长或批量加载。
4. 检查 requests/limits 是否与实际运行峰值匹配，避免只提高 limit 而不定位内存增长原因。

## 常见原因与处理

### 原因1：内存泄漏

**特征**：内存随运行时间持续上升，流量下降后仍不回落，重启后暂时恢复。

**处理方案**：在重启前保留堆转储；定位未释放引用；修复后通过长时间压测验证内存曲线。

### 原因2：大批量加载或大文件处理

**特征**：固定任务或上传时内存短时突增，处理结束后理论上应释放。

**处理方案**：改为流式或分页处理；限制上传大小；将重任务放入后台队列；控制单批数据量。

### 原因3：内存 limit 设置不足

**特征**：内存增长符合正常流量，接近固定 limit 时被杀，应用无明显泄漏信号。

**处理方案**：依据峰值和安全余量调整 limit；同时核算节点容量；不要超过节点可调度资源。

## 验证与预防

验证容器不再出现 OOMKilled、重启次数稳定、内存有合理余量，核心接口成功率恢复。监控容器内存、重启原因、GC 和大对象分配；对导入、压缩和批任务设定资源预算。
