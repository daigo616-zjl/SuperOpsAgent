# 消息队列积压告警处理方案

## 告警名称

- **告警名**: `MessageQueueBacklog`
- **告警级别**: 警告；积压持续扩大或超过业务时效时升级为严重
- **触发条件**: Topic 或 Queue 的积压消息数连续 10 分钟增长，或消费延迟超过业务允许时限。

## 业务影响

消息积压会延迟异步任务、订单状态同步、通知发送和数据处理。积压持续增长时，恢复后可能出现集中消费，对下游数据库、第三方接口或缓存造成突发压力。

## 排查步骤

### 步骤1：确认积压范围

检查哪些 Topic、消费组和分区出现积压，比较生产速率、消费速率和消费延迟。确认是单一分区热点还是整个消费组处理能力不足。

### 步骤2：检查消费者状态

确认消费者实例是否在线、是否频繁重启、分区分配是否均衡，以及是否存在持续失败或反复重试的消息。

### 步骤3：分析处理耗时和下游依赖

检查单条消息处理耗时、批量大小、并发度，以及数据库、Redis、外部 API 的延迟和错误率。消息消费慢往往是下游依赖变慢的结果。

### 步骤4：检查生产端突增

确认是否有营销活动、批处理回放、上游重试或异常重复投递导致生产速率突然提高。

## 常见原因分析

### 原因1：消费者实例异常或数量不足

**特征**：在线消费者数减少；消费速率显著低于生产速率；实例日志有崩溃或重启记录。

**处理方案**：恢复异常消费者；在分区数允许的前提下扩容消费者；检查频繁重启根因后再恢复稳定消费。

### 原因2：下游数据库或外部接口变慢

**特征**：消费者仍在线，但单条处理耗时升高；下游慢查询、连接等待或 API 超时同步出现。

**处理方案**：优先修复下游瓶颈；对非关键消息实施限速或暂停；避免盲目扩容消费者把压力进一步传递给下游。

### 原因3：毒消息导致重复失败

**特征**：同一消息或相同业务键反复失败；错误日志集中在固定异常；消费位点推进缓慢。

**处理方案**：记录失败原因和消息标识；对确认无法处理的消息转入死信队列；修复逻辑后进行受控重放。

### 原因4：分区热点或消费不均衡

**特征**：只有少数分区积压；部分消费者空闲而部分繁忙；消息 Key 高度集中。

**处理方案**：优化消息 Key 分布；调整分区策略；对热点业务键实施拆分或串行化处理。

## 紧急处理措施

1. 先判断积压是否仍在增长，以及是否影响业务时效。
2. 恢复异常消费者并确认消费位点正常推进。
3. 对下游压力敏感的 Topic 限速，避免恢复时雪崩。
4. 对毒消息隔离到死信队列，禁止无限重试。

## 验证步骤

1. 消费速率持续高于生产速率。
2. 积压消息数和消费延迟持续下降。
3. 消费者无连续重启和重复失败。
4. 下游数据库、缓存和外部接口保持在安全负载。

## 预防措施

- 监控生产速率、消费速率、积压量、消费延迟和失败率。
- 为毒消息设计重试上限和死信队列。
- 压测消费者吞吐量及下游依赖容量。
- 为峰值流量预留分区和消费者扩容能力。
