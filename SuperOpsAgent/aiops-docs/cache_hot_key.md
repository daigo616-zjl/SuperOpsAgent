# Redis 热点 Key 告警处理方案

## 告警名称与影响

- **告警名**: `RedisHotKey`
- **触发条件**: 单个 Key 的 QPS 持续高于实例平均水平 10 倍，或该 Key 所在分片 CPU、命令延迟连续 5 分钟升高。

热点 Key 会使单个 Redis 节点成为瓶颈，表现为命令延迟升高、应用读取超时；若热点失效，还会形成大量回源请求并冲击数据库。

## 排查步骤

1. 通过 Redis 慢日志、命令统计或业务埋点确认高频 Key、访问 QPS 和所属节点。
2. 关联应用日志，确认热点来自正常活动、循环重试、爬虫流量还是异常请求。
3. 检查 Key 的数据大小、TTL 和序列化开销；大 Key 与热 Key 同时出现会放大延迟。
4. 检查缓存未命中后的数据库 QPS，确认是否已有回源放大。

## 常见原因与处理

### 原因1：正常业务热点

**特征**：活动、榜单或热门商品在固定时间段访问集中，Key 内容正确且请求来源正常。

**处理方案**：将热点数据预热到本地缓存或多副本缓存；对读请求做分片；为热点 Key 设置合理 TTL，避免同时失效。

### 原因2：异常重试或爬虫请求

**特征**：同一客户端、接口或参数在短时间内重复访问，日志中存在大量失败重试。

**处理方案**：对来源实施限流；修复客户端无限重试；对无效参数提前拒绝，避免请求进入缓存层。

### 原因3：大 Key 读取开销高

**特征**：单次返回数据量大，网络带宽和序列化耗时升高，Redis CPU 随读取 QPS 上升。

**处理方案**：拆分 Key；只读取必要字段；限制单个 Key 大小；将大对象改为分页或按字段存储。

## 验证与预防

验证该 Key 的 QPS、实例 CPU 和命令延迟回到基线，应用不再出现读取超时，数据库回源 QPS 保持稳定。持续监控 Top Key、慢命令、大 Key、命中率和缓存回源量；为活动场景预先压测并设置限流与预热方案。
